# テスト方針

更新日: 2026-10-24

## チケットごとの実行ルール

各実装チケットで、変更の影響を受けるテストを実行し、実行コマンドと結果をチケットに記録する。上流の変更で影響を受ける既存機能の回帰確認も行う。統合テストは機能チケットで必須。画面・利用者操作が関わるチケットはE2Eテストも必須。適用できない層は理由を記録する。

単体テストだけで完了にしない。テストが失敗した状態、テスト未実行、受け入れ条件の未確認がある状態でチケットを完了にしない。テスト対象外の仕様書・調査チケットも、リンク整合性や対象データの件数など、チケットに対応する確認を記録する。

| 層 | 確認する範囲 | 例 |
|---|---|---|
| 単体 | 一つの関数・部品の規則 | 語彙順位付け、コサイン類似度、キー割り当て競合、時刻・集計 |
| 統合 | HTTP・サービス・DB・ファイル・API境界の組み合わせ | 語彙回答保存、移行と復元、候補登録、教材と語彙IDの関連付け |
| E2E | ユーザーがブラウザで行う重要シナリオ | A/U・S/Iで語彙を学び記録を見る、カテゴリの苦手語から教材を作って再生する |

テストピラミッドは単体を広く、統合を主要経路すべて、E2Eを少数の重要シナリオに絞る。E2Eは壊れやすい実装詳細ではなく、利用者の受け入れ条件を検証する。

## テスト用データ

`tests/fixtures/`に、バージョン管理できる小さな合成データを用意する。語彙だけの大量データではなく、機能間の関係・境界条件を組み合わせる。

- 複数カテゴリ・タグ、複数の語義、品詞、CEFRあり／なし、同綴異義語・語形変化。
- 未学習、正答のみ、誤答のみ、混合履歴、日→英／英→日それぞれの履歴、旧方向不明の履歴、同時刻に見える履歴。
- 類似語の閾値直下・直上、完全一致、意味の近い語、表記が同じ別語、ゼロ／欠損ベクトル、片方向の旧similar。
- 1語も使われない教材、対象語の一部／すべてを使う教材、複数文への分割、保存MP3参照、破損JSON・欠損音声。
- API成功・空・構造不正・タイムアウト・レート制限の応答を再現する固定応答。

テストデータは匿名化の名目で実ユーザー語彙・履歴をコピーせず、人工的なサンプルを作る。ケースと期待値をデータセットREADMEに記録し、固定シードを用いる。現行DBの規模感を確認する必要があれば、値を持ち出さず読み取り専用集計で比較する。

## 分離・再現性・課金防止

- テストごとに一時ディレクトリのDB・教材ディレクトリを初期化する。テスト後に破棄し、`dataset/vocab.db`や`practice_data`を開かない。
- APIキーがなくても動くよう、OpenAI境界を差し替えて固定応答を使う。自動テストは外部ネットワークへ接続しない。
- 実APIで行う手動スモークテストは自動テストから分ける。明示的に必要なときだけ少量で実行し、使用モデル・日時・件数・料金・結果を記録する。費用が確認できない限り実施しない。
- E2Eのブラウザ・ドライバが未整備なら、T-003で軽量なツールを選定し、起動方法・固定待機条件・スクリーンショット等の証跡・ローカル実行コマンドを決める。
- CI導入時も同じコマンドを使い、秘密鍵や実データはCIへ渡さない。

## 現在の実行手順

Windows上でNode.js 20.19以上を用意し、`npm ci` を実行する。PlaywrightのChromiumを用意して `npm test` を実行する。`npm test` の先頭でReact + TypeScriptの型検査とVite production buildも行う。

```powershell
npm ci
npx playwright install chromium
npm test
```

`npm test` はTypeScript型検査/Vite build、Python unittest、キー操作のNode tests、Playwright E2Eの順で動作する。Vite buildは `english_overlap/static/app/` にproduction成果物を生成する。E2Eサーバーは `tests/e2e_server.py` がOS一時ディレクトリにDBと教材を作る。OpenAI境界は固定応答へ差し替え、音声は合成WAV fixtureを使う。Playwrightは操作ごとに要素状態を待ち、固定sleepは使わない。スクリーンショットは `tests/e2e-artifacts/` に生成され、`.gitignore`により管理外となる。

GitHub ActionsはWindows上で同じ `npm test` を実行し、APIキーを渡さない。CIに使うのは `npm ci` / `npx playwright install chromium` / `npm test`。

## テストデータ導入順

T-014で共通フィクスチャ、DB生成・リセット、API差し替え、実行手順を作る。以降のチケットは不足する境界ケースを追加してfixtureを育てる。テスト用データと本番データの件数・完全一致性を要件にしない。受け入れ条件に必要な代表ケースが揃っていることを優先する。

## チケット完了記録テンプレート

各チケットに次を記録する。

```text
統合テスト: [コマンド] — 成功/失敗/未実施（理由）
E2Eテスト: [シナリオ・コマンド] — 成功/失敗/未実施（理由）
テストデータ: [fixture名・追加/変更したケース]
その他の確認: [結果]
未確認: [あれば記載]
```
