# T-073: Make SQLite the sole source of truth for saved materials

- Status: Complete
- Priority: P1
- Requirements: DATA-006, DATA-007, DATA-008, DATA-009, DATA-010
- Dependencies: T-071, T-072

## Background

T-072 corrected summary mismatches by declaring practice_data JSON canonical and SQLite a mirror. That still stores the same material in two mutable forms. The user selected the database as the single canonical store. Material text, title, summaries, generated speech/transcript/timings, and generation metadata must be read and written in SQLite; audio binaries remain files.

## Scope

- Included: Add durable structured material content to SQLite; import existing valid saved JSON into SQLite once with a pre-migration backup and per-file audit; preserve existing material IDs, archive state, vocabulary links, and audio references; make material lists, details, playback subtitle/timing data, edits, summaries, archive/delete, and new audio generation use SQLite; stop creating or updating subtitle JSON; retain safe audio file cleanup; leave unimportable legacy JSON in place and report it.
- Excluded: Deleting old JSON files automatically, migrating vocabulary/history, changing audio formats or OpenAI models, and merging arbitrary DB-only materials.

## Acceptance criteria

- [x] SQLite is the only read/write source for all structured material metadata after a one-time, idempotent import of legacy JSON. Imported content and metadata survive restart; DB edits are never overwritten by legacy JSON on subsequent list reads.
- [x] Existing valid JSON files are imported without losing article body, title/summary provenance, blocks, transcript, word timings, voice/style/model, cost/counts, audio reference, creation time, material ID (when already mapped), archive state, or vocabulary links. Invalid/unreadable JSON is reported and retained. Import is transactional per file, audited, and preceded by the application's SQLite backup migration.
- [x] Both material lists are DB-backed and agree; playback loads subtitle/timing data by material ID from SQLite and the audio file from its safe audio path. New generation stores structured results in SQLite and writes only audio binary files. No new subtitle JSON is created.
- [x] Summary generation and edits mutate the DB only; body edits clear stale timing/transcript data and detach (but do not delete) prior audio. Delete/archive keep existing safety and shared-file behavior. DB-only materials are visible wherever appropriate and no longer depend on JSON membership.
- [x] Isolated migration, HTTP, and UI tests cover successful, repeated, partial/invalid import, mismatch repair once, persistence after source mutation, DB-only entries, generation/playback/edit/summary/delete, and no production DB/practice_data/API access.

## Test plan

- Integration: Isolated DB and legacy-file fixtures verify atomic per-file import, preservation of linked state, one-time behavior, DB-only edits and summaries, generated content saved in SQLite, and safe cleanup.
- E2E: Open imported materials, play via DB-loaded transcript/timing plus audio, create a material and generate audio without subtitle JSON, edit and summarize, then reload and verify all content remains DB-backed.
- Other validation: Build, `git diff --check`, and relevant complete suite per `docs/testing.md`.

## Implementation

Added migration v5 with structured `content_json` and a durable one-time legacy-import ledger. Lists, saved details, playback subtitles/timings, summaries, edits, generation, and deletion now use SQLite; audio files remain separate. Import preserves mapped IDs, status, vocabulary links, and available content, reports invalid files, and cannot overwrite a source already imported. Subtitle JSON is no longer generated or updated. Fixed asynchronous saved-material refresh/reselection after revisiting the overlap tab.

## Limitations

Legacy JSON files remain on disk as inert migration artifacts for recovery. Their later edits are intentionally ignored; material edits and summaries must be made through the application so SQLite remains canonical. Audio binaries remain files.
