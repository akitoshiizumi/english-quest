# T-079: Prevent duplicate vocabulary registration

- Status: Complete
- Priority: P1
- Requirements: none (candidate registration reliability and data integrity)
- Dependencies: T-078

## Background

The “選択した候補を登録” button remains active while the request is in flight. The database checks normalized headwords, but the UI can still submit the same selection repeatedly and the server should explicitly treat completed or excluded candidate IDs as idempotent, including under concurrent requests.

## Scope

- Included: Disable registration while a request is pending, restore it after a recoverable error, and make candidate selection idempotent under repeated requests and normalized duplicates.
- Excluded: A global uniqueness constraint on spelling, since distinct senses and existing data may share headwords.

## Acceptance criteria

- [x] The registration button disables immediately and cannot send a second request while the first is pending; success locks the completed selection and failure allows retry.
- [x] Repeating the same candidate selection, including concurrent/retried HTTP submissions, creates at most one vocabulary/sense pair; normalized duplicate candidates in one request also create at most one.
- [x] Existing headwords and candidates already excluded as duplicates or similar are not registered by a stale or crafted request.

## Test plan

- Integration: `py -m unittest tests.test_http_integration -v`; submit identical selection requests twice and assert one vocabulary/sense record.
- E2E: `node --test --test-concurrency=1 --test-name-pattern="candidate deduplication|vocabulary preview batches|vocabulary preview reports|candidate registration" tests/e2e_learning.cjs`; delay mocked registration and verify duplicate clicks send one request; verify failure retry.
- Other validation: `npm.cmd run build`; `git diff --check`.

## Test data / fixtures

- `DatabaseMigrationTests.make_legacy_db` copied into a temporary directory and migrated; no live database is used.

## Implementation

The registration UI now locks the selection during the request and allows retry after an error. `select_candidates` uses its existing immediate transaction to skip already-created/excluded rows, recheck normalized headwords, and update its lookup map after each insert. No schema uniqueness constraint was added.
