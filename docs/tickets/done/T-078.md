# T-078: Make vocabulary preview batch similarity checks and report progress

- Status: Complete
- Priority: P1
- Requirements: none (candidate preview performance and reliability; related to vocabulary similarity behavior)
- Dependencies: T-077

## Background

The saved-material vocabulary preview creates a separate similarity request for every word and runs all requests concurrently. Large materials can appear to hang, while concurrent request accounting writes collide in SQLite (`database is locked`). Each request also reloads and decodes the full dataset embedding set, repeating substantial local work.

## Scope

- Included: Compare candidate vocabulary in bounded sequential batches with one Embeddings API request and one accounting/job update per batch; show live progress and recover cleanly from errors; load the dataset vectors once per batch and use an exact-safe cosine upper-bound pruning step before exact scoring.
- Excluded: Changing the embedding model, similarity threshold meaning, existing index content, or introducing a third-party numerical dependency.

## Acceptance criteria

- [x] Preview of a material with more than one batch completes by submitting bounded sequential compare requests, not one concurrent request per word.
- [x] Progress and processed/total counts update after each batch; errors stop the spinner, preserve visible completed preview rows, and allow retry.
- [x] Each batch sends candidate strings together to the Embeddings API, records aggregated usage once, persists assessments in one write, and never exposes raw candidate vectors in the HTTP response.
- [x] Similarity results preserve exact-match and cosine-threshold behavior; the optimized scorer skips exact dot products only when a mathematically safe upper bound is below the threshold.
- [x] Concurrent database-lock failures from preview's per-word fan-out are eliminated; batch endpoint failures produce a normal HTTP error/job failure without an unhandled server traceback.

## Implementation

The preview now sends candidates in sequential batches of 50. The server embeds each batch in a single Embeddings request, loads a cached compact dataset prefix index, uses a safe cosine upper bound to avoid unnecessary exact comparisons, and transactionally persists assessments, usage, and job completion. The browser reports completed/total candidates and can resume after a failed batch.
